    Engine requests¶

    urbansolarcarver.engine_requests turns a request message into an engine call and a reply. Every transport uses it: the daemon today, a local HTTP service later. It does not import torch until a request runs.

    • parse_engine_request(message) validates a dict into one of the request models below, or raises MalformedEngineRequest (a ValueError) when the message is not a dict, names an unknown command, or lacks or misuses a key.
    • config_for_engine_request(request) builds the config: from the YAML file in config with overrides on top, or, without a file, from the starting values of the mode the overrides name (load_config.build_config_from_mode_starting_values).
    • handle_engine_request(request, session, context=None) runs the request inside a run context and returns a reply model; engine errors propagate. A given RunContext receives progress, issues and cancellation.
    • answer_engine_message(message, session) does all of this for transports that carry dicts and never raises: any failure becomes an error reply.

    Commands¶

    run runs the stages needed to produce produce, through the same sequencer as run_pipeline().

    Request key Meaning
    produce List of stages to produce: preprocessing, thresholding, exporting, massing
    run_folder The folder that holds one subfolder per stage
    start_from First stage to run (default preprocessing); earlier stages are read from run_folder
    config Optional path of a YAML config
    overrides Optional list of key=value strings, or a mapping

    Without config, the config is built in memory from the starting values of the mode named in the overrides (mode is required) with the overrides on top; no file is written.

    The reply holds stage_folders (stage name to folder, only for the stages that ran in this call), manifest (the manifest of the last of them), issues, and export_path (exporting), plates_path, mesh_path (the OBJ) and export_mesh_path (the plates in final_mesh_format) (massing) for the stages that produced them.

    preprocessing, thresholding, exporting, massing run one stage. They need config; every stage but preprocessing also needs from, the upstream stage's folder or manifest. out_dir defaults to <config out_dir>/<stage>. The reply has issues and manifest, export_path (exporting) or plates_path, mesh_path and export_mesh_path (massing).

    run_pipeline runs preprocessing, thresholding and exporting into out_dir (default: the config's out_dir); Grasshopper definitions saved before run existed still send it. simulate_weights writes a simulated-weights file (epw, archetype, out, optional internal_gains_w_m2 and eps) and replies with artifact and preview. ping replies with the process id (pid).

    Keys a command does not use are ignored. Reply fields that are None are left out.

    Replies¶

    Every reply to a run or stage command has issues, a list of {stage, code, message}. An error reply has error (the text), error_type (the exception class name; MalformedEngineRequest for a malformed request) and, for a ConfigError, config_errors, a list of {field, message}.

    urbansolarcarver.engine_requests ¶

    Requests the engine answers, shared by every transport.

    A transport (the pickle daemon today, an HTTP service later) receives a message; this module turns it into an engine call and a reply:

    • :func:parse_engine_request validates a message into one of the request models, or raises :class:~urbansolarcarver.errors.MalformedEngineRequest.
    • :func:config_for_engine_request builds the request's config: from its YAML file with the overrides on top or, without a file, from the starting values of the mode the overrides name.
    • :func:handle_engine_request runs a request inside a run context and returns a reply model; engine errors propagate to the caller.
    • :func:error_reply_for turns an exception into an error reply.
    • :func:answer_engine_message does all of this for transports that carry plain dicts, and never raises.

    Stopping a transport is the transport's own business, not a request here. Importing this module does not import torch: the stage functions are imported when a request runs.

    parse_engine_request(message) ¶

    Validate message (a mapping with a cmd key) into a request model.

    Raises:

    Type Description
    MalformedEngineRequest

    If message is not a mapping, names an unknown command, lacks a required key or holds a value of the wrong type.

    config_for_engine_request(request) ¶

    The validated config of request.

    With config (a YAML path) the file is loaded with the overrides on top; without it, the config is built from the starting values of the mode the overrides name. Raises ConfigError for invalid settings and FileNotFoundError for a missing YAML file.

    handle_engine_request(request, session, context=None) ¶

    Run request and return its reply; engine errors propagate.

    session is the transport's CarverSession (anything with a release_memory method); unused GPU memory is released after every run or stage request, successful or not, while the session cache stays. context receives progress, issues and cancellation; a new one is used when it is None.

    error_reply_for(exc) ¶

    The error reply for exc: its text, its class name and, for a ConfigError, the invalid fields.

    answer_engine_message(message, session) ¶

    Parse and run message and return the reply as a dict; never raises.

    Any failure becomes an error reply; failures other than a malformed request are also logged with their traceback. Reply fields that are None are left out.
