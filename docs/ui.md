# Browser UI

`usc ui` opens UrbanSolarCarver in your browser. You add the maximum volume and the test surfaces, choose a mode for a criterion and the test surfaces it protects (a project can carve with several criteria, one after the other), run the analysis, adjust how much to carve while watching the result in 3D, build the envelope and building massing, and download the files. It runs the same engine as the CLI and the Python API; everything stays on your computer.

## Starting the interface

In the UrbanSolarCarver folder, double-click `start-urbansolarcarver.bat` on Windows, or run `./start-urbansolarcarver.sh` in a terminal on Linux and macOS. The first time, the launcher installs UrbanSolarCarver with `setup_env.py` (this takes several minutes and needs Python 3.10 or newer); after that it starts the interface at once. A window stays open while the interface runs: close it (Windows) or press Ctrl+C (Linux, macOS) to stop UrbanSolarCarver. The launcher passes its arguments on to `usc ui`, so `start-urbansolarcarver.bat --port 8780` works too. It uses the environment in `.venv` in the folder, or `~/.usc-venv` when `setup_env.py` had to put it there; for an environment made with `setup_env.py --venv-dir`, set `USC_VENV` to that folder.

From a terminal with the environment active, the same command is:

```bash
usc ui
```

The command prints the address to open and opens it in your default browser once the service is listening. When another program already uses the port, the command says so and stops without opening the browser; choose a free port with `--port`. The address carries a token that is new on every launch, so keep using the page it opened (or the printed address) and not a bookmark from an earlier launch. Press Ctrl+C in the terminal to stop the service.

| Option | Default | Meaning |
|--------|---------|---------|
| `--port` | `8770` | Port on `127.0.0.1` |
| `--projects-folder` | the folder chosen in the app, else `~/UrbanSolarCarver/projects` | Folder that holds one subfolder per project; it is created when missing. It wins over the folder chosen in the app for that launch |
| `--no-browser` | off | Print the address without opening the browser |
| `--device`, `-d` | `auto` | Compute device: `auto`, `cpu` or `cuda` |

The browser interface is an optional extra of the package. `setup_env.py` installs it unless you pass `--no-ui`; to add it to an existing environment run `python -m pip install -e ".[ui]"` (see [Installation](getting-started/installation.md#browser-ui)). Without the extra, `usc ui` prints that command and exits, and every other command is unaffected.

When the service starts it compiles the GPU kernels in the background. The start screen shows "Preparing the GPU" until that ends; you can open a project and add files meanwhile, and the run buttons wait for the GPU.

## The start screen

The start screen, headed **Projects**, has three cards side by side (one above the other in a narrow window):

- **New project**: type a name (up to 64 letters, numbers, spaces, hyphens or underscores) and create the project. The project opens with its setup window (see [A new project](#a-new-project)).
- **Open a project**: the projects in the projects folder, newest first, and at the foot of the card the folder (on one line, the whole path on hover) with **Change folder**. Each project has a menu (see [Managing a project](#managing-a-project)).
- **Try an example**: three projects with their files already in place, so you can run an analysis without preparing any input. *Perimeter block* (a perimeter block 126 by 92 m, mode Sun hours) is the smallest, *New building among neighbors* (a plot of about 18 by 17 m among existing buildings, mode Solar energy) is the middle one, and *District of many buildings* (about 208 by 227 m, mode Solar energy) is the largest. The first time you choose an example, it makes a copy as a new project, so the example itself never changes. After that, choosing it opens that project again. A project records which example it came from, so it is found after a rename. To start from a fresh copy, use **Reset to the example** in the project's menu.

A small footer under the cards gives the version and the GPU's name, or why the CPU is used. While the GPU warms up, a one-line notice above the cards says so.

### The top bar

- **UrbanSolarCarver** at the left returns to the start screen when a project is open (it is a button: Tab to it and press Enter). Leaving Inspect with turned surfaces not saved asks first.
- The project's name with its menu, the **Settings** button (see [Project settings](#project-settings)) and the **Carve | Simulate | Inspect** switch, while a project is open.
- The device's state at the right: "GPU ready" (the GPU's name on hover), "Preparing the GPU", "CPU mode", or "GPU not available" with its reason. Beside it, once a run of the open project has finished in this page, how long the last one took, "Last run 7.0 s": the whole run, a pipeline run or a simulation, from its start to its last event. It is not kept when the page is reloaded, and a narrow window leaves it out.
- The **theme button** at the right end: a moon switches the whole app to its dark theme, a sun back to the light one. The 3D view follows the theme. The choice is kept in the browser's storage for the address of the app, so a launch with another `--port` starts in the light theme.

### Project settings

The **Settings** button in the top bar (a gear) opens the settings every criterion shares, in a window over the page. It is there in Carve, Simulate and Inspect. Its tooltip gives the weather file's location, north and the voxel size, "THESSALONIKI, GRC. North 10°, 0.5 m voxels" ("No weather file. North 0°, 1 m voxels" without one). While one of these settings has to be fixed, the button shows the red **!** of a step row, and a screen reader hears "Settings, 1 setting to fix".

The window holds these settings, with plain labels, units and a help text for each:

- **Location**: the **weather file** (`.epw`), a box like those of the Site step, with **Add files** (then **Replace**) at the right of its title, the location the file gives (city and country) and × to remove it, and a line naming the modes that need it; and **North direction** (°).
- **Account for context blocking**: with context or terrain in the Site step, on by default; off, they still take their voxels but block no sun or sky, to compare the two carvings. Without either it is greyed out and says what to add. The Angle rule traces no rays to the sky and does not read it.
- **Voxel size** (m), with the size of the voxel grid and the sample spacing on the test surfaces under it. A grid larger than the analysis can handle is refused here, with the smallest voxel size that fits.
- Under **More detail settings**, **Rays per sky patch** (1, 4, 9 or 16; the same for every criterion, and for Simulate's studies; Sun hours and Angle rule do not use it) and **Rays per batch**, which changes the speed and the memory a run uses, not its results. A project that kept rays per sky patch in its criteria, from before 2026-11-09, takes the value of its first criterion that is on.
- **Carving**: **Update the carving as I change its settings**, on by default: a change of a criterion's carving rule carves again at once; off, **Update carving** does, in the bar pinned under the steps or on the view's Out of date stamp. It is kept in the project, and can be changed during a run.
- **Heights**: the **Base height**, below which nothing is carved, and, for a project made from sites, the **Max height**. See [Base height and max height](#base-height-and-max-height).

The sample spacing on the test surfaces, the grid margin and the ray length have no field: the engine's values apply (see [Entering values](#entering-values)). Each change is saved as it is made, as in the steps; there is no Apply. A change puts every criterion out of date. While a run is in progress the fields wait and say why. The settings of the envelope, the building massing and the export are in their steps, next to their builds. **Done**, × and Escape close it, and the focus goes back to the button.

Run analysis is in the Criteria step. When a setting of this window blocks it, the reason names the window, "Fix the voxel size in Settings to run the analysis", and **Open settings** under it opens the window on that field. A missing weather file does the same: "Add a weather file in Settings to run Daylight", with **Open settings**, which opens the window on the weather file's box. The **Go to** link of a run that failed on one of these settings does the same.

### A new project

A project made with **Create project** opens with **Set up the project** over it: the project settings a page at a time, with the page count at the top ("1 of 3"), **Back**, **Next**, and **Skip setup** at the left of the buttons.

1. **Location**: the weather file and North direction, the same group as in [Project settings](#project-settings).
2. **The site**: two tiles, **Sites** (outlines drawn in the view, each raised to a height) and **Maximum volume** (mesh files of the largest building allowed). A tile chooses that input, as the tiles of the Site step do (see [A site as the input](#a-site-as-the-input)), and goes on to the heights.
3. **Heights**: base height and, for sites, max height, as in Settings (see [Base height and max height](#base-height-and-max-height)).

Each change is saved as it is made; nothing is required. **Start**, on the last page, closes the window and opens the Site step; with Sites it starts drawing the first site. **Skip setup**, × and Escape close it at any page and keep what was set. The window is shown once, when the project is made: a project that is opened, or made from an example, has none. Everything in it is in Settings and the Site step afterwards.

### The projects folder

**Change folder** opens the operating system's folder picker on this computer. The browser never sends a path: the service shows the picker and reads the folder you choose. The folder is remembered in `~/.urbansolarcarver/ui.json` and used at the next launch. The projects already in the old folder stay there, and the list shows the projects of the new folder.

- **Change folder** is offered on the start screen only, with no run active. While a run is active the start screen says the folder can be changed once the run has ended.
- When the folder was given with `--projects-folder`, it wins for that launch and the start screen offers no Change folder. Start `usc ui` without the option to change it there.
- When the folder picker cannot open (no display, or tkinter missing), the start screen says so and the old folder stays. The way that always works is to start with `usc ui --projects-folder <folder>`.

### Managing a project

Each project in the list, and the project name in the top bar, has a menu:

- **Open folder** opens the project's folder in Explorer (Finder, or the file manager on Linux) on this computer. It works during a run.
- **Rename** asks for a new name, checked by the same rule as a new project's name, and renames the folder.
- **Delete** names the project and its folder and asks you to type the project name to confirm.
- **Reset to the example** (projects made from an example) replaces the project's inputs, settings and results with a fresh copy of the example, after a confirmation. The project keeps its name.

Rename, delete and reset wait while the project's run is active.

Delete and Reset send the project folder to the recycle bin (Windows) or trash (macOS, Linux), so a mistake can be undone; UrbanSolarCarver does not delete it for good. They remove only that one project folder, and refuse when the folder is not a direct child of the projects folder, has no `project.json` of that project, or is or holds a symbolic link or junction. On Windows they work only for a folder on a fixed disk of this computer: on a network, removable or other drive they are refused, and you can delete the folder in the file manager. A folder larger than the recycle bin's size limit may be deleted for good by Windows, and the app cannot check this beforehand.

## The steps

A project opens as a list of four steps on the left, with the 3D view on the right. Each step shows a one-line summary when it is closed.

1. **Site.** The boxes come in this order: **Context**, **Test surfaces**, **Terrain**, then **Sites** (or **Maximum volume**), so what is around the site is added, and test surfaces picked on it, before the site is drawn. The site's geometry: the maximum volume (the largest building you would allow), from mesh files or drawn as sites (see [A site as the input](#a-site-as-the-input)). Then the project's **Test surfaces**, which the criteria (step 2) and the studies choose among (see [Test surfaces as sets](#test-surfaces-as-sets)); the weather file is in [Project settings](#project-settings). The step was called Inputs in earlier versions; the project folder still keeps its files in `inputs/`. Two boxes are optional: **Context** (buildings and large trees that stay, `context_path`; not balconies or shading devices) and **Terrain** (the ground, `terrain_path`). Both block sun and sky; nothing is built in the columns the context takes, and the site stays buildable above the terrain (see [Context and terrain](modes.md#context-and-terrain)). Removing their files makes the analysis out of date, and the next run goes without them. With either of them, **Account for context blocking** in the [project settings](#project-settings) can turn their blocking off, to compare the two carvings. Meshes may be PLY, OBJ, STL, GLB or DXF; several files for one role are joined into one. A DXF file is read for its faces (`3DFACE`, polyface and polygon-mesh polylines, `MESH`, in blocks too), in the drawing's units (millimetres, centimetres, inches and feet become metres; a drawing without a unit is read as metres); a DXF of closed polylines and no faces is refused, with a pointer to **Import** in the Sites box. Removing a file (×) takes it out of the project and its calculations but does not delete it: the stored copy moves to `inputs/removed/<role>/` in the project folder (a second file of that name there becomes `name (2).ply`), so a file removed by mistake can be added again from there. Right after a removal the box says "*name* was removed." with **Undo**, which adds the file back (a surface set with its name and picks) until the next upload or removal; under the boxes, "*n* removed files are kept in the project folder." with **Show**, which opens `inputs/removed/` in the file manager (`POST /projects/{name}/inputs/{role}/restore`, `GET /projects/{name}/removed-inputs`, `POST /projects/{name}/removed-inputs/open-folder`). The step lists each file by name; its triangle count, and for a test surface set the criteria and studies that use it, are in the tooltip of its remove button. Under **Overall size** it gives the size of all inputs together, and warns when the model looks as if it is not in meters. Every box has its title on the left and its action on the right of it (**Add files**, or **Draw** and **Import** for the sites), whether it has files or not; a muted line under the title says "Optional" for the context and the terrain. Under that, every box says in a line what geometry it expects (for the terrain: "The ground. It blocks sun and sky; the site stays buildable above it."), whether it has files or not. An empty box is dashed and adds "You can also drag files onto this box." The Sites box no longer repeats the heights set for all sites; they are in Settings.
2. **Criteria.** A criterion is one carving pass with its own test surfaces, mode and carving rule. The step shows one of two views: the **list** of criteria, or the **editor** of one criterion. A new project has one criterion: the step first shows the six mode tiles, each with its tooltip, and choosing one sets its mode and opens its editor. Examples and projects whose mode is chosen skip this. The views, **Add criterion** and the pinned bar are described under [Several criteria](#several-criteria). The run the project needs and **Build envelope and massing** stay pinned under the steps while the step is open. The editor has a header and three sections:
    - **The header**, which stays at the top of the step while the sections scroll under it: **All criteria** (back to the list); "1 of 3" with **Previous criterion** and **Next criterion** buttons when there are two or more criteria; the colour dot, the name (up to two lines), the symbol of the mode, the on/off switch and the menu; and the result line (one line, the whole line on hover).
    - **The sections**, each a button with the section's title and, while it is closed, a one-line summary of what it holds. Only **Carving rule** is open when the editor opens; **Test surfaces** and **Settings** are closed. The sections you open or close stay as you left them when you open another criterion.
        - **Test surfaces** (summary: the file name, two file names, "3 files" or "None yet"): the test surfaces the criterion protects (the surfaces whose sun or sky the carving protects), chosen among the project's: a hint of what its mode may protect (Daylight: windows or facades; Solar energy: roofs or facades), then one switch per set of the Site step's Test surfaces box, with its triangle count. While none is on, Run analysis waits. A project without test surfaces says so here, with **Open the Site step**.
        - A criterion's mode is set when it is made and does not change: the top of **Settings** names it. For another mode, add a criterion in it and delete this one. The tooltip of a mode tile holds a one-line description, what the mode needs and the engine name, for people who use the CLI.

        | Tile | Engine name | What it does |
        |------|-------------|-------|
        | Angle rule | `tilted_plane` | Removes everything above a plane at a fixed angle from each facade |
        | Sun hours | `time-based` | Keeps direct sun on the test surfaces during the hours you choose |
        | Solar energy | `irradiance` | Keeps sun and sky energy over the period |
        | Solar heating | `benefit` | Keeps sun in the hours that need heating |
        | Daylight | `daylight` | Keeps the view of an overcast sky |
        | Night cooling | `radiative_cooling` | Keeps a flat roof's view of the cold night sky. Experimental, and it assumes horizontal test surfaces |

        Choosing a mode fills its starting values in the Settings section. [Carving Modes](modes.md) explains the methods.
        - **Settings** (summary: the analysis period in words, "21 Dec, 7 to 19 h", in the modes that have one; otherwise "Starting values" or "2 settings changed"): the analysis period, the mode's own settings and, under **Detail settings**, the rays per sky patch in the four sky-patch modes. Settings that most people leave alone are folded under a header with a chevron, like the sections of the panel, named for what they hold: **More mode settings**, **More sun settings**, **More carving settings**, **More detail settings**. In Solar heating the section starts with **Which hours count**, Cold hours or Energy-weighted (see [The typical building](#the-typical-building)).
        - **Carving rule** (summary: "Carve 70 %", "Cutoff 1.5 m²·h", "Automatic", or "Everything above the planes" in the Angle rule): how much to carve, with a histogram of the scores of the voxels (a log or linear scale). What the carving removed is on the criterion's card. The rule's info "i" sits beside Manual | Automatic. In the weighted modes the *Carving rule* comes first: *Manual* (the *Carve amount* slider, in percent of the total score) or *Automatic* (no setting: the cut is found from the spread of the scores, and the step says where it fell). A cutoff on the scores that a config holds (from the command line or an earlier version) shows as Manual, at the carve amount it stands for. Sun hours has a *Shade allowed per voxel* slider in m²·h; the Angle rule has no threshold. The histogram follows the control in both rules; the other carving settings (score smoothing, the cut above a carved voxel, the steepest slope of the envelope) are folded at the end, under **More carving settings**. Scores are in physical units: m²·h of shade each voxel casts (Sun hours), kWh of solar energy or of useful solar heat each voxel blocks (Solar energy, Solar heating), and m² of fully hidden sky each voxel hides (Daylight, Night cooling); the histogram axis, the cutoff, the 3D legend and the slider ends say which. Before the first analysis it says to run the analysis.
    A section with something to fix opens by itself, so a new criterion opens with Test surfaces open, and its summary turns to the warning colour, with a warning icon (screen readers hear "Needs attention" in its header): no test surfaces; a weather file the mode needs and the project lacks (Settings, whose summary reads "Needs a weather file"); settings the last save refused (Settings or Carving rule, where a closed section says "2 settings to fix" in place of its summary). A criterion that is off needs neither test surfaces nor a weather file, and its closed Carving rule reads "Off". A **Go to** *setting* link in a refused run opens that criterion's editor, then the section that holds the setting, and focuses the field.

    The step's summary joins the mode and the carving: "Solar heating, 56 % kept". With several criteria it lists each one with the share it kept: "Daylight on windows 70 %, then Solar heating 80 %". A criterion that is off reads "Solar heating, Off", and with every criterion off the summary is "All off".
3. **Envelope and massing.** Two parts that are built on their own, since the massing reads the carving and not the envelope.
    - **Envelope**: its settings (smooth surface, smoothing passes, the smallest pieces and fragments kept), **Build envelope**, and its result, the envelope volume (counted on the kept voxels the mesh was built from, after small pieces are dropped, not on the smoothed surface).
    - **Building massing**: its settings (ground floor and upper floor heights, grid module, permitted volume exceedance, whether floors rest on the floors below), **Build massing**, and its results: the gross floor area, the number of storeys and a table with the bottom, top and floor area of each storey.

    Each part has its own out-of-date mark, "Out of date for the current settings". The step's summary says what exists, for example "Envelope built, massing not built". A link at the bottom opens the run report. The *grid module* is the square module the storeys are built from and the narrowest piece of floor allowed. The *permitted volume exceedance* is the share of a module on a storey that may lie outside the carved envelope; the massing never leaves the maximum volume. [Floor-plate massing](massing.md) describes the method.
4. **Export.** The mesh format of the carved envelope and the building massing, and the downloads: the carved envelope, the building massing, the building massing data (JSON), the settings (`config.yaml`) and the whole project as a zip. Each file is offered once it exists. The envelope and the massing are the files that were built, in the format they were built in. A change of format rebuilds the parts that exist (the envelope, the massing or both); while the carving is locked (see below), the format is stored without a build, Export says so, and the next build of each part writes the chosen format.

## A site as the input

A project makes its maximum volume either from mesh files or from **sites**: closed outlines drawn in the 3D view, each raised to its own height. A new project shows two tiles at the top of the Site step, **Maximum volume** and **Sites** (or chooses in its setup window); once one is chosen the box shows that input only. A link at the bottom left of the box changes it ("Draw sites instead", "Use a maximum volume instead"); when the input has content it asks first and says the results will go out of date. The other input's files or sites are kept, so switching back restores them. Projects made before sites existed open with their mesh files.

**The rule.** A site's outline is the polygon of its vertices in plan: at least 3 vertices, no crossing edges, at least 1 m². Each vertex carries the elevation of the ground there, in the coordinates of the other input files. The ground along an edge runs straight between its two vertices; inside the outline it is the shape a stretched membrane takes on that boundary (a harmonic function, computed on points about 1 m apart), so it never rises above the highest vertex or falls below the lowest. The site's volume stands on that ground and has a flat top at its **lowest vertex plus its height**. A site whose height is not more than its rise (its highest vertex above its lowest) is refused, with the rise in the reason. Several sites are joined into one maximum volume, as several files are. Sites may share an edge or a vertex but not an area: a change that makes two sites overlap, or puts one wholly inside another, is refused (see [Holes in sites](#holes-in-sites)). The ground inside a site only shapes the volume: it blocks no rays (a terrain file does). The service builds the volume (`sites.py`); the engine carves it as it carves a mesh.

**The Sites box.** **Draw** and **Import** are at the right of its title (see [Importing sites](#importing-sites)). Under it, a table with one line per site: its name, a column for each height set per site (**Base height** and **Max height**, in m, see below), and a menu with Rename, Edit outline, **Place on terrain**, **Restore original** (an imported site whose outline changed) and Delete. A double click on a name renames the site. The name's tooltip gives the plan area and the elevations above the lowest vertex ("Elevations 0 to 4 m"), which also show under the site while it is edited. A height that the site refuses is shown in red with its reason and not saved. **Draw** starts drawing. While the Site step is open, a click on a site in the view edits it.

**Drawing.** The view turns to the top view, north up (orbiting still works), and a bar at the top gives the steps. Each click adds a point on the drawing level: the lowest vertex of the sites, or for a project's first site the lowest level of the existing surroundings and terrain, else 0. A dashed line follows the pointer with the length of the segment. The pointer snaps to the first point, which closes the outline, and to the vertices and edges of the other sites, so neighbouring plots share their boundary; Shift holds the segment at a multiple of 15° from the previous one. Enter closes the outline, Backspace removes the last point and Esc cancels. The new site is saved with the height of the last site (30 m for the first) and opens for editing.

### Holes in sites

A site may have **holes**: closed outlines strictly inside its outline where nothing is built, such as a courtyard. The volume leaves a hole out from the ground to the top: each hole's vertices carry the ground's elevation, the ground's boundary follows the hole's edges as it follows the outline's, and walls go up every ring. The lowest vertex and the rise count the holes' vertices too, so a hole whose ground is lower than the outline's lowers the top. A hole must have at least 3 vertices and 1 m², must not cross itself, must lie strictly inside the outline (touching it is not inside), and must not touch or cross another hole; a site breaking any of these is refused with the reason ("Block: hole 1 is not strictly inside the outline."). A site's area is its outline's minus its holes'. The base volume leaves the holes out too.

**In the Sites box.** A site with holes says so in its details ("2 600 m², 1 hole · Flat"), and each hole has a line under its site ("Hole 1") with **Delete hole** in its menu. A hole is drawn on purpose: **Draw hole**, beside Undo and Redo in a site's editor, draws a closed outline as **Draw** does and makes it a hole of that site, its vertices at the site's lowest elevation, to be set like any other; a hole that does not fit (not strictly inside the outline, touching another hole) is refused with the reason, and Esc or Cancel goes back to the site's editor. One undo takes back the hole. **Edit outline** edits the holes' vertices too, in the same undo history (moving, adding on an edge, removing down to 3, typing an elevation); the handles are named "Hole 1 vertex 2". **Place on terrain** and **Restore original** include the holes.

Two sites **overlap** when their areas share more than a line and neither lies in a hole of the other; sites that share an edge or a vertex do not overlap. A change that makes sites overlap is refused (user, 2026-11-12): a drawn site, an outline moved onto another site, or a site put wholly inside another ("Site 2 lies inside Block: draw a hole in Block instead."). Overlaps a project already has (made before they were refused) are kept, and warned about, until one of the two sites' outlines is edited; a change elsewhere (a rename, a height, another site) is stored with them. `GET` and `PUT /projects/{name}/sites` list the overlapping pairs in `overlaps` (`first`, `second`, and `inside` when the first lies wholly inside the second, so it could be its hole). Under the table the box says "Site 2 and Site 3 overlap: check their outlines." for each pair, or "Courtyard lies inside Site 1: make it a hole of Site 1, or move it.", and the rows of those sites carry a warning sign. A site lying wholly inside another has **Make a hole of *Site 1*** in its menu (not while it has holes of its own, which would be lost): one change, in the undo history, turns it into that site's hole. This is how a courtyard imported as a separate site before holes existed becomes a hole; until then the carving fills the courtyard.

### Importing sites

**Import** in the Sites box (or a file dropped on it) reads the closed polylines of a DXF or OBJ file; each becomes a site, added after those there and checked by the same rule as a drawn one.

- DXF: `LWPOLYLINE` and 2D and 3D `POLYLINE`, in blocks too, in the drawing's units as above. A polyline is closed by its closed flag or by ending on its start. Arcs in a polyline become straight segments no more than 5 cm off the arc. A site is named after its layer; several on one layer are numbered ("Plots 1", "Plots 2").
- OBJ: polylines (`l` lines), closed when the last index repeats the first, as Rhino writes them; named after their object or group.
- **Nesting.** An outline wholly inside another becomes a hole of the smallest outline around it; an outline inside a hole is a site again (an island in a courtyard), and so on: an outline inside an even number of others is a site, inside an odd number a hole. An outline that shares an area with an earlier outline of the file, or with a site already in the project, is left out ("B: it overlaps A"). Holes of one outline that touch each other are left out ("the holes of Block: hole 1 and hole 2 touch or cross"), and the outline stays a site without them.
- **Elevations are relative.** Each vertex takes its height above the lowest vertex of all outlines in the file, from the level a drawn site starts at: the lowest vertex of the sites there, or for the first sites the lowest level of the surroundings and terrain, else 0. A flat outline lands flat on that level; a 3D outline keeps its slope; outlines of one file keep their levels relative to each other; elevations in survey coordinates do not move the model. x and y are taken as they are.

Before anything is added, a window shows what the file holds: the outlines with their area and rise, what was left out (open polylines, lines, circles, outlines the site rule refuses, by name), a warning when the outlines lie more than 1 km from the other inputs in plan, and, with terrain, **Place on terrain**, on by default. **Import n sites** adds them as one change in the sites' undo history (Ctrl+Z while a site is edited), and frames the view.

An imported site is edited like a drawn one. Its outline as imported is kept with it, and the file in the project folder (`inputs/sites/`): **Restore original** in its menu puts that outline back.

**Place on terrain** sets each vertex of a site, imported or drawn, to the top of the terrain below it. Vertices with no terrain under them keep their elevation, and the box says how many. It needs a terrain file and uses the terrain only, not the surroundings. It is an edit like any other, in the same undo history, and a later change of the terrain does not move the site.

### Base height and max height

Two heights bound what the carving may decide, each measured from a site's lowest vertex:

- **Max height**: the top of the site's volume, as above. It can be a height that is not negotiated, or one high enough to let the carving find the largest form.
- **Base height**: nothing below it is carved, in any criterion; the carving decides only the volume between the two heights. Use it for the current or the permissible uniform height, to read the result as what can be built above it without harming the test surfaces. Empty means no lower limit, as before.

In **Settings › Heights** each height has a switch: **Global**, with its value there, or **Per site**, typed in each site's row of the Sites box. A new project starts Global, with a base height of 0 m and a max height of 50 m; a base height of 0, like an empty one, is no lower limit. A Global height has no column: one line above the table says it, "Global: base 8 m.", with **Change in Settings**, which opens Settings on that field. The sites keep their own values while the switch is on Global, so switching back to Per site restores them. A site whose max height is not above its base height is refused, with the reason in its row. A new site takes the project's values, or the height of the last site while the max height is Per site. With a mesh maximum volume, Heights has the base height only: one level above the lowest point of the mesh, which is the upper limit.

With a base height, the part of the maximum volume below it is a layer of its own, **Base volume**, drawn as the light solid (the service cuts it at the base levels: `GET /projects/{name}/base-volume`). The **Maximum volume** layer is always drawn as dotted edges (fainter in the later steps); with a base height it starts hidden, so switch it on in **Layers** to see the max height. A change of a max height builds the maximum volume again and puts every criterion out of date. A change of a base height puts only the carving out of date: the analysis stays current, and the next run carves again in seconds. With a base height, a criterion's card adds what the base kept and what was built above it, "Base kept: 54 000 m³. Built above it: 12 400 m³ of 31 000 m³ (40 %)"; the share is of the volume between the two heights, and so is the Carve amount. When the base alone holds a quarter or more of the obstruction of the test surfaces, the card says so: carving above it cannot remove that.

**Editing.** Each vertex has a handle labelled with its elevation above the site's lowest vertex. Drag a handle to move the vertex in plan; its elevation stays. Click it to type its elevation, in the input files' coordinates; the height above the lowest vertex is shown beside it. Double click an edge to add a vertex there (its elevation interpolated along the edge); Delete removes the selected vertex (a site keeps at least 3). Every change is saved, and Ctrl+Z and Ctrl+Shift+Z (or Ctrl+Y) undo and redo the changes of the sites. A change that would make the site refused is not saved: the outline is drawn red and the bar says why. Esc deselects the vertex, then ends the editing.

### Test surfaces as sets

The **Test surfaces** box of the Site step holds the project's test surfaces as **sets**: each file added is a set, and so is each group of faces picked on the context. A row shows the set's name; the tooltip of its remove button adds its triangle count, "picked on the context" for a picked set, and "Used by" the criteria and studies that use it. **Add files** (or a drop on the box) adds sets; **From context**, there with context files, picks them in the view. Each row has a menu, **Rename** and, for a picked set, **Edit picks**, and a remove button. A set added or picked is used by nothing until a criterion or study switches it on; taking it out of a criterion or deleting the criterion keeps it in the project. A set that a criterion or study uses cannot be removed: its remove button is disabled and says by whom ("Used by Daylight: switch it off there to remove it"). Sets no criterion uses are drawn in the Test surfaces layer under "Test surfaces no criterion uses".

### Picking test surfaces on the context

**From context** in the Test surfaces box of the Site step picks whole faces of the context as test surfaces; picking ends when the step closes. A bar at the top of the view says what to do. A click on the context picks the **flat piece** under the pointer: the clicked triangle and those reached from it across shared edges whose normal is within 1° of its own and whose corners lie within 1 cm of its plane. A facade made of several triangles is one piece, a facade with openings cut out is one piece with holes, two walls meeting at a corner are two pieces; corners within 0.1 mm of each other count as one. A click on a picked piece drops it. The terrain cannot be picked (a terrain's many tilted triangles wait for drawing on surfaces, a later step).

The bar chooses where the picks go: a **New set**, named "Picked n" to start with, or **Add to** an existing picked set. **Use n faces** stores the set (`POST /projects/{name}/surface-sets/picked`), which then waits in the box for a criterion or study to switch it on; Esc and Cancel send nothing. Each piece is turned to face the side it was clicked from, whatever the winding of the context file, so a facade clicked from the street faces the street; a test surface lying on a facade still sees out, as rays start 1 cm off it.

A picked set keeps its picks (the point clicked and the direction of the click). **Edit picks** reopens picking with its faces, to add or drop some, and **Save picks** stores them again; every criterion and study that uses the set reads the new faces. When the context files change, each picked set is built again from its picks; a pick that finds no face any more is dropped from the set and its row says so ("2 picked faces are gone from the context").

## Several criteria

A project can carve with several criteria in turn, for example the daylight of the neighbours' windows first and then the winter sun on a yard. Each criterion has its own test surfaces, mode, mode settings and carving rule, and decides among the voxels the criterion before it kept ([Criteria: chained carvings](criteria.md) explains the method). The Criteria step is built for this from the start: it shows the list or one criterion's editor, and **Add criterion** under the list starts a chain.

### Which view the step shows

- The first time the Criteria step opens after a project opens, a project with one criterion shows that criterion's editor, and a project with two or more shows the list. After that the step remembers whether it showed the list or an editor, and which criterion, while the project stays open, also across a rename of the project, and also when a run ends and opens the step. Deleting criteria down to one does not open the editor by itself.
- Pressing a card, **Add criterion** (the new criterion) and **Duplicate** (the copy) open an editor, and the focus goes to the criterion's name in its header. Nothing else moves the focus into an editor: the step opening on one, **Previous criterion** and **Next criterion**, and a link that opens an editor leave it where it is (a link to a setting puts it on the field). **All criteria** returns to the list, with the focus on that criterion's card. **Delete** in the menu of an editor also returns to the list, with the focus on the card selected after the delete.
- Anything that leads to one criterion's setting opens that criterion's editor first: a refused run, the **Go to** *setting* link of a refused run or a failure, and the notice of a new weather file, which belongs to the criterion it offers a new period to (while it waits, opening the Criteria step opens that criterion's editor).

### The list

The list has one card per criterion, in carving order. A card shows:

- a colour swatch, the criterion's colour in the 3D view's by-criterion layer, and the symbol of its mode;
- the criterion's name, whole, on up to two lines across the card, under the swatch and the symbol (the whole name also on hover);
- the result line under the name, at the card's full width. When the criterion is current it says what it removes, "Removes 70 % of the obstruction" in the weighted modes or "Removes 62 % of what reached it" in the others (the first criterion receives the maximum volume, each later one what the criterion before it kept); otherwise its state:

| Line | Meaning |
|------|---------|
| Out of date | Its test surfaces or settings changed after its last run, or a shared setting did |
| Updates from *name* | A criterion before it is out of date or running, so this carving will change when that one finishes |
| Running | The run is tracing or carving it now |
| Off | Switched off: the chain skips it |
| Choose test surfaces | It protects nothing yet, and a run waits for a set to be switched on |
| Not run yet | It has test surfaces and no result |

- a **›** at the right end of the card's first row, after the switch and the menu, which says that the card opens. Pressing the card, or Enter or Space on it, opens the criterion's editor. The criterion opened last stays marked as selected, and the 3D view keeps showing its layers: the kept voxels are the ones left after it.

A card also has:

- a switch that means on, **Use** *name*. It is on by default, and a new criterion is on. Switching it off leaves the criterion out of the chain without deleting it: the card reads "Off" and the editor says "Off: the chain skips this criterion" in place of its carving rule. Switching it on again brings the rule back;
- a menu with **Rename**, **Duplicate** and **Delete**. Duplicate copies the settings and the test surface files into a new criterion at the end and opens its editor. Delete asks first: the criterion's settings and results go; its test surfaces stay in the project's Test surfaces box. The criteria left keep their switches: when the one left is off, it stays off and Run analysis waits with "Turn on a criterion to run". The only criterion cannot be deleted (the item waits with "A project needs at least one criterion.");
- with two or more criteria, a drag handle: drag the card to reorder, or focus the handle and press the up or down arrow key. Reordering puts out of date the carving of the criteria from the first changed position on. A single criterion has no handle.

The drag handle, the switch and the menu keep their own actions and do not open the card. When the selected criterion is deleted, the selection moves to the next card, or to the previous one when it was the last. Switching the selected criterion off keeps it selected. While a run is active the cards, the switches and the menus wait.

**Add criterion**, under the last card, opens a short menu of the six modes, each with its symbol, its plain name and its one-line description under "Mode of the new criterion". Pointing at a mode, or reaching it with the arrow keys, shows the tooltip of its tile beside the menu. Choosing a mode adds the criterion at the end of the chain, named after its mode, and opens its editor; its Test surfaces section is open, since it has none yet. The arrow keys, Home and End move in the menu, and Escape closes it and returns to the button. While a run is active **Add criterion** waits; a run that starts while the menu is open makes its items wait, with the reason under them.

Under **Add criterion**, with two or more criteria on, a line gives what the chain kept: "After all criteria: kept 48 % of the maximum volume". It is the volume left after the last criterion that is on, as a share of the maximum volume as drawn. Without that share there is no line.

### The editor of a criterion

The editor takes the place of the list inside the step, and the step stays open. It is the header and the three sections described under [Criteria](#the-steps), for one criterion. The header sticks to the top of the step while the sections scroll under it. Under **All criteria** and the position ("2 of 3") are the colour swatch, the mode symbol, the switch and the menu, then the name, whole on up to two lines across the header, then the result line. **Previous criterion** and **Next criterion** open the criterion before or after in carving order, and save what you typed as pressing a card does; the focus stays on the button, and a screen reader hears the criterion's name and position ("Daylight, 3 of 3"). At the first criterion **Previous criterion** waits, and at the last **Next criterion** waits, without losing the focus. With the list gone from above, the carving rule starts about 196 px below the top of the editor when the criterion's name fits on one line, and about 216 px when it takes two: the header is 95 or 115 px, the sections start 4 px under it, and a closed section's header is 32 px. Before the first run the carving rule says to run the analysis. A closed section's summary stays on one line. With several criteria:

- The **Test surfaces** section lists every set of the project with a switch, so two criteria protect the same set by switching it on in both. A set is stored once, and switching it off in one criterion leaves it in the others.
- The carve amount and the histogram of the second criterion on refer to the voxels the criteria before it kept, so 80 % in the second criterion is 80 % of the score of what is left.
- **Update carving** and **Update the carving as I change its settings** carve again from this criterion on, without tracing: moving the cutoff of criterion 1 thresholds criteria 1 and 2 again in one run, criterion 2's card reads "Updates from *name*" (the name of criterion 1) until it finishes, and criterion 1's histogram keeps its own scores. No analysis runs, and the bar offers no run meanwhile. Once it finishes, a line under the buttons names the criteria it carved, "Carving updated: Daylight, Solar energy.", so changing criterion 2 of three names 2 and 3 only; with one criterion it reads "Carving updated." The line stays until the next run, or until a change puts the chain out of date. When another criterion has an analysis that is out of date, the change is saved and nothing runs; the step says "Run the analysis for *name* first", and Run analysis traces that criterion first.

### The pinned bar

The bar pinned under the steps while the Criteria step is open, in the list and in an editor, holds the run the project needs and **Build envelope and massing**, side by side, so they are in view with any section open or closed. The run is **Run analysis** while the analysis of a criterion that is on is missing or out of date, and **Update carving** while only a carving is (the update is off, or the criteria were reordered or switched on or off); it carves as Update carving in the Carving rule section does. With everything current there is no run to offer: the bar holds only the build, as its primary button. The progress of a run, its refusals and the failure of a carving update are under them; the warnings of the last run fold behind one line, "2 warnings", which opens their list, while a failure and "Cancelled." are said in full. When the progress is long and the window short, the bar scrolls within its height and the step above stays reachable. With several criteria a reason names the criterion it is about, the one open too: "Add test surfaces to Daylight to run the analysis", "Add a weather file to run Daylight", "Fix the analysis period of Daylight to run the analysis". **Build envelope and massing** waits, with its reason under it, while the analysis is missing ("Run the analysis before building"), out of date ("Settings changed: run the analysis again before building"), or current with a carving that is not ("Update the carving before building"), and while a run is active.

### What the criteria share

The maximum volume, the surroundings and the terrain are set once in the Site step, and the [project settings](#project-settings) (the weather file, north, the surroundings switch, voxel size and, folded, the rays per sky patch and the rays per batch) apply to every criterion, as do the settings of Envelope and massing and Export. A change to any of them puts every criterion out of date. A setting belongs to a criterion when the service lists it in `GET /api/criterion-keys` (the mode's settings and the carving rule); the app takes the split from there. The weather file reaches only the criteria whose mode reads one.

### Runs

**Run analysis**, in the Criteria step's pinned bar, shows while an analysis is missing or out of date. It traces the rays of the criteria whose test surfaces, mode settings or a shared setting changed, then carves the chain from the first of them on. There is one Run analysis for the whole chain and no button per row. After adding a second criterion to a finished project, the next run traces only the new one. The progress lists the stages of each criterion, "Daylight on windows: Sun analysis" and "Daylight on windows: Carving", then the envelope and the massing; with one criterion the rows keep their plain names. A run that calculates the [typical building](#the-typical-building) first has the row "Typical building" before them.

A refused run points at the criterion that caused it, in the pinned bar and in that criterion's editor:

- A setting of one criterion that the engine refuses opens that criterion's editor, says so in the bar with a **Go to** *setting* link, and marks the field. The link opens the section that holds the setting (Settings or Carving rule) and focuses the field.
- The warnings of a run are said in plain words, by the code the engine gives each one, with the numbers read from its message: "Every voxel was carved: the threshold is probably too low." for the engine's "all-False mask". A warning about one setting has a **Go to** *setting* link beside it, which works as the link of a refused run: the threshold, the score smoothing, the edge strip, the plane angle, the sun altitude, the balance temperature, the night dew point, the analysis period, rays per batch, the grid module. A warning of a criterion other than the one open starts with that criterion's name. The engine's own wording is folded under the list ("As the engine wrote them"), for the config names. A code the app does not know is shown as the engine wrote it.
- A criterion that protects nothing opens its editor with the Test surfaces section open; the bar says "Choose test surfaces for *name*." **Run analysis** waits with "Choose test surfaces for *name* to run the analysis" while any criterion that is on has none. When that criterion is not the one shown, **Open *name*** beside the reason shows it with its Test surfaces section open, and its card's status line is marked with a warning sign.
- With every criterion off, the run waits with "Turn on a criterion to run".

A run that is cancelled or fails keeps what it finished: the next run starts with the first stage that did not finish, so the criteria before it are not traced again.

A test surface the run leaves out (not flat, too small for the grid, or without area) protects nothing. The layer **Skipped test surfaces** draws them in the error colour, and the Layers menu says how many and why, as in "8 of 43 surfaces not protected: 8 not flat". The layer is there only when a run left a surface out, and shows the criterion selected. It reports what the run did: the app does not check the files before a run, or repair them.

A result file that is gone from the project folder makes its stage missing, so the next run writes it again. A voxel, sky dome, envelope or massing result that is there and cannot be read shows greyed in the Layers menu, with a note that its file may be damaged.

**Build envelope and massing** waits until every criterion that is on is carved, and builds once, from the last criterion.

### The 3D view with several criteria

- The layer **Carved voxels, by criterion** (Layers menu, hidden until you turn it on) draws each carved voxel in the colour of the criterion that removed it, and the legend, "Carved voxels, by the criterion that removed them", names each colour. The layer appears once every criterion that is on has run; the menu says so until then. It is dimmed with the other results while any criterion is out of date. Beyond 1,000,000 carved voxels it draws a regular share of them, and the legend says which ("Showing 1 of every 2 voxels").
- The layer **Test surfaces** draws each criterion's files in the colour of that criterion, all at full strength. With two or more criteria its entry in the Layers menu has a check box and a colour swatch for each criterion, in chain order (a criterion that is switched off reads "name (off)"), all checked until you change them; the **Test surfaces** check box shows or hides the layer as the other layers' do (half checked while some criteria are unchecked) and does not change which criteria are checked. Sets no criterion uses are a last entry, "Test surfaces no criterion uses", drawn without a criterion's colour. A file that several criteria use is drawn once, in the colour of the selected criterion when it uses the file and is shown, else in the colour of the first shown criterion that uses it. Which criteria are shown stays as you set it when you select another criterion or open another step, and is not saved with the project. The sun path and the sky dome follow the selected criterion.

### The run report

With several criteria the run report's Criteria section has one row per criterion: name, mode, rule, cutoff with its unit, voxels at start and voxels kept. A **Chain** section follows, with the maximum volume (the filled voxels the first criterion started with), the volume left after each criterion in m³ and its share of the maximum volume in %. The total time adds the analysis and carving of every criterion to the exporting and the massing. A report of one criterion has no Chain section. The Configuration, Preprocessing and Thresholding sections describe the last criterion.

### Earlier projects

A project made with an earlier version opens as a chain of one criterion: one card in the list, its results still current, and the test surfaces it protected as sets in the Site step, switched on in its only criterion. A project that was carved further with an earlier version keeps its maximum volume (the last envelope) and the note under it in the Site step, "Carved by Daylight, then Sun hours. The earlier maximum volumes are kept in the project folder, in inputs/earlier_max_volumes." **Carve further** is no longer in the app: add a criterion to carve what the first one kept, which also leaves no mesh between the criteria to voxelize again.

## The typical building

A Solar heating criterion counts the sun of some of the hours of its analysis period. **Which hours count**, a two-way switch at the top of its Settings section, says which:

- **Cold hours** (the default): the hours colder than the balance temperature minus the dead band, the rule of [Carving Modes: benefit](modes.md#benefit). The balance temperature slider is under the switch.
- **Energy-weighted**: each hour counts by what its sun saves a typical building in heating over the year, from a simple hourly model of one room. The engine and its documentation call this model 5R1C, the hourly method of ISO 13790 ([Simulated Benefit Weights](simulated-weights.md)); the app does not use the name. The balance temperature is hidden and not read; its values are kept, so Cold hours brings them back. The **Cold period from the weather file** preset of the analysis period is not offered with Energy-weighted: it belongs to the cold hours rule.

With Energy-weighted, a **Typical building** box under the switch names the library entry the building came from ("Apartment, zone Β", or "Changed from Apartment, zone Β" once a value differs from it), the state of its weights ("Calculated", "Changed since it was calculated" or "Not calculated yet", the last two with "Run analysis calculates it first.") and **Edit building**. A new project has no typical building: the box says "None chosen" and "Choose one from the library to run the analysis.", and its button, **Choose building**, opens the window on the library. Until one is chosen, Run analysis with an energy-weighted criterion that is on is refused as a missing input, with "Choose a typical building for the energy-weighted criteria: Edit building, in the Settings of the criterion." A project whose building was stored with the keys of an earlier form of the values (before 2026-10-29) reads as none chosen.

A project has one typical building, shared by all its energy-weighted criteria: a copy of a library entry, which the project keeps with the entry's name. **Edit building** opens a window in the middle of the screen, over the app, which is dimmed behind it. The focus moves to the window's title and stays inside it. The window closes with **×**, Escape or **Done** at the bottom right, and the focus goes back to Edit building. There is no Cancel: a value is saved as it is typed. The window is up to 880 px wide (never more than the screen less 32 px) and up to the screen's height less 64 px. In a window 900 px wide or more it has two columns: on the left the **Library** and the groups of values, which scroll on their own, and on the right **Calculate**, the chart and the numbers, which stay in view while the left column scrolls. In a window under 900 px wide it is one column. It holds:

- **Library** (folded, open while no building is chosen; its line names the entry, or "Changed from" it, and the source of an example is in small print under it): the examples, read-only, in groups named by the source of their values (*Greece, KENAK reference building*: "Apartment, zone Α" ... "Office, zone Δ"; see [Simulated Benefit Weights: the library examples](simulated-weights.md#the-library-examples)), then **Your buildings**, each with **Rename** and **Delete**. Choosing an entry replaces the project's copy with its values. Without a building, the window holds only the library and **Done**, with the note "The project has no typical building yet: choose one to start from, then change its values." The library is apart from projects (one file per own entry in `~/.urbansolarcarver/typical_buildings/`), so an own entry serves every project; changing or deleting an entry does not change a project that took it.
- **Save to library** writes the values over the own entry the building came from (an example cannot be changed: the window says so and offers **Save as new**); **Save as new** asks a name and adds an own entry, which the building then comes from. A name is used once in the library, letter case aside.
- Three folded groups, each with its values in one line while it is closed: **Use** (the hours in use, one of three cases, *Residential: 6:00 to 24:00 every day*, *Office: 8:00 to 18:00, Monday to Friday* and *Always*; the comfort band, from and to, in °C (the room runs free, with no heating or cooling: the sun counts where it warms the room while it is colder than the band, and against where it warms it above); internal gains while in use in W/m²; fresh air while in use in m³/h per m² of floor; heat recovery 0 to 1), **Fabric** (U of the walls and of the windows in W/m²K, the whole-window g, and the thermal capacity in kJ/m²K of floor, one number) and **Summer shading** (one factor for every window, 0 to 1, where 1 lets all the sun through and an empty field is no shading, with the day and month it starts and ends). The form offers no lists of standard values: its values come from the library's examples or from the user.
- **Advanced**, folded, with three more groups: **Room** (the average room or a box; storey height and room depth for the average room, a square turned 45° with walls facing NE, SE, SW and NW; width east to west, length north to south and orientation for a box; the glazed share of each wall, 0 to 0.9), **Roof and floor** (each adiabatic unless switched to exposed, then with its U) and **Air** (infiltration in air changes per hour, in every hour; the temperature above which the windows open when outdoors is cooler, as far as needed to bring the room back to it, and the most air open windows let in, in air changes per hour; 25 °C and 4 in the examples). Switching the room turns an average room of depth d into the box 4d × 4d turned 45°, and a box into the average room with the same facade per m² of floor.
- **Calculate**, about 5 s, with a bar under the button that fills as the calculation goes (the app asks the service how far it has come every half second), then **Effect of sunlight, by hour**, drawn at the width of its column: one chart with the days of the year across and the hours of the day down, red where the sun warms the room below the comfort band, white where it has no effect and, when the criterion counts harm, blue where it warms it above the band (benefit minus harm); the hours with the sun down are grey. Three numbers follow: the room's degree-hours below and above the band a year, each with its hours (**Below the comfort band**, **Above the comfort band**; weights calculated before 2026-10-31 show the conditioned room's heating and cooling in kWh/m² instead), and the daytime hours whose weight is above 0.01 (**Hours that count**). On the Golden, CO weather file "Apartment, zone Β" spends 32,363 degree-hours below the band and 1,965 above it a year, and 2,409 of the 4,438 hours with the sun up count.

A number is saved when its field is left or Enter is pressed, the other controls on the change. The library's own dialogs (Save as new, Rename, Delete) open over the window. A value the model cannot use is refused with the reason under its field (a window share above 0.9, a comfort band whose upper limit is not above its lower one, windows opening below the band, a date that does not exist, walls that lose too much heat for the thermal mass), its group's line turns to the warning colour (and Advanced opens for one of its groups), and Calculate waits until it is fixed. Calculate also waits for a weather file. After the building or the weather file changes, the chart and the numbers are dimmed and the button reads **Calculate again**. While a run is active the window says why its values wait.

Run analysis does not need Calculate first: when it analyses an energy-weighted criterion whose weights are missing or out of date, it calculates them before the sun analysis, as the progress row "Typical building". A changed building puts out of date only the energy-weighted criteria. The weights are written to `inputs/typical_building/weights.json` in the project folder (with a picture of them, `weights.png`), which the project's `config.yaml` names as `simulated_weights_path` for each energy-weighted criterion, without its balance values.

## Criteria in a project

A project holds an ordered list of **criteria**, the carving passes of a chain (see [Criteria: chained carvings](criteria.md)). Each has its own mode, test surfaces, mode settings and carving rule, and decides among the voxels the criteria before it kept. Every project holds at least one: deleting the only criterion is refused with a 422 (*A project needs at least one criterion.*).

The app asks for a criterion's settings and results by its id. A client that does not name one (the routes keep their meaning for a project with one criterion) gets, for a project with several, the settings of the first criterion and the results of the last one that is on (the score colours, the sky dome and the run summary's top-level carving). Settings are saved with `PUT /projects/{name}/shared-settings` and `PATCH /projects/{name}/criteria/{id}`.

**Where a criterion's data lives**

- `project.json` lists the criteria: id, name, colour, whether it is bypassed (the field the app's on switch sets, the other way round), the names of its test surface files and its own settings. A criterion's id is `"1"`, `"2"`, and so on, assigned by the service, kept when the criteria are reordered and never used again in the project. Run folders and joined test surface files are named by id.
- `config.yaml` is generated from `project.json` at every change: the settings shared by the whole chain at the top, then the criteria that are on under `criteria:`. A bypassed criterion is left out, and so is left out of every run. A project folder is still valid input for `usc run -c <folder>/config.yaml`. Change settings in the app, because the next save writes the file again.
- `inputs/test_surfaces/` stores each test surface file once, named as uploaded. `inputs/joined/test_surfaces_<id>.ply` is the joined file the engine reads for criterion `<id>`.
- `run/criteria/<id>/preprocessing` and `run/criteria/<id>/thresholding` hold each criterion's results, with `run/criteria/chain.json` listing them in order. Exporting and massing stay in `run/exporting` and `run/massing` and are built once, from the last criterion that is on.

**Test surface files**

- Each stored test surface file is a **surface set**, shared by name: the criteria and the studies list the sets they use. A set is shown by its name: the file name without its extension for an upload, "Picked 1", "Picked 2" for picks, or one given with **Rename** (unique in the project, letter case ignored). Renaming changes only the name shown; the stored file keeps its name, which the routes, the joined files and Inspect use.

- An upload with the content of a stored file reuses that file. An upload with the name of a stored file and other content replaces it in every criterion that uses it, and puts out of date only those criteria. A set stays in the project until it is removed in the Test surfaces box.
- A set stays in the project until it is removed through the inputs route; removing it from a criterion or a study, or deleting a criterion, keeps it. A criterion or a study uses a set through the *use* route, which adds no copy.
- A new criterion has no test surfaces. A run refuses to start while no criterion is on (the app's Run analysis waits with "Turn on a criterion to run") or while one that is on protects nothing (*Choose test surfaces for <name>.*). The checks a run starts with look at the criteria that are on only: the settings of each must validate, and the weather file is needed when one of them reads it. A bypassed criterion needs nothing. A criterion is named after its mode as the app shows it ("Sun hours", "Daylight", ...) until it is renamed; one that gets its first file and has not been renamed is named "<mode> on <file name>", for example "Daylight on roofs". A project from an earlier version names its criterion 1 the same way.
- The Site step's Test surfaces box adds and removes sets through the inputs routes with the role `test_surfaces` (`POST /projects/{name}/inputs/{role}`, `DELETE /projects/{name}/inputs/{role}/{file_name}`), as the other roles do; a removal is refused with a 422 naming the criteria and studies that use the set. A file with the name of a stored set and other content replaces it, and the criteria and studies that use it are joined again. A criterion's switches use its routes (`PUT` and `DELETE` on `/projects/{name}/criteria/{criterion_id}/test-surfaces/{file_name}`); `POST /projects/{name}/criteria/{criterion_id}/test-surfaces` still uploads a file straight to a criterion, for the API. `InputFileInfo.used_by` lists the names of the criteria, then the studies, that use a set.

**Settings routes**

- `PUT /api/projects/<name>/shared-settings` saves the settings the criteria share (voxel size, north and the like) from a body `{values}`, with no mode; the values are merged into the stored shared settings. A key that is a criterion's own setting is refused with a 422 that names it, and so is a value that makes any criterion that is on invalid or a grid over the budget. Nothing is stored then. The reply holds the shared settings as stored and the `grid_plan`.
- `GET /api/projects/<name>/criteria/<id>/settings` answers `{criterion_id, settings}`: the criterion's settings with the shared ones, without the paths and device the service owns.
- `GET /api/projects/<name>/sun-path` takes an optional `criterion` (default: the first criterion that is on, the first one when none is).
- A 422 that comes from one criterion's settings (a refused run start, a rejected `PATCH` of a criterion) carries `criterion`, its id, next to `field_errors`.
- The project list's `mode` is the mode of the first criterion that is on. `criteria` in the run summary gain `volume_removed_m3`, the volume a criterion removed (null without results).

**What goes out of date**

| Change | Out of date |
|---|---|
| Maximum volume, context, terrain, weather file or a shared setting | Everything |
| A criterion's test surfaces (a file added, removed or replaced) | Its preprocessing, then the thresholding of every criterion that is on from it on |
| A criterion's own mode settings | The same |
| A criterion's carving rule (carve amount, threshold, smoothing, `carve_above`, slope limit) | Its thresholding, then the thresholding of every criterion after it |
| Order, switching a criterion off or on, or deleting one | The thresholding of every criterion that is on from the first changed position on |

Exporting and massing are compared with the settings of the last criterion that is on and with its thresholding. When the last criterion is deleted, the one before it becomes the last, and exporting and massing are out of date.

`GET /api/projects/<name>/stage-status` answers with `stages`, as before (preprocessing and thresholding sum up the criteria: missing when any is missing, else out of date when any is, else current), and `criteria`, the state of both analysis stages of each criterion that is on, in chain order. The project detail repeats it as `criterion_status`.

**Running**

A run traces the rays only of the criteria whose preprocessing is missing or out of date, then thresholds the chain from the first traced criterion on, or from an earlier criterion whose thresholding is out of date. When no criterion needs tracing and a thresholding is out of date, it thresholds the criteria that are on from the first out-of-date one on; the ones before it keep their results. A criterion that only needs thresholding again does not trace. `StartRunReply.criterion_stages` says what the run does for each criterion that is on, for example `{"1": [], "2": ["preprocessing", "thresholding"]}` after a second criterion was added to a finished project. The service sends the engine `trace_criteria` for this, and `threshold_from_criterion` when thresholding starts at another criterion than the first traced one, or than the first one when nothing is traced (see [Engine requests](api/engine-requests.md)). The progress and issue events of a run carry `criterion`, the id of the criterion the stage belongs to, or null for exporting and massing.

**Results**

- `GET /api/projects/<name>/run/summary` keeps its fields (`carving` describes the last criterion that is on) and adds `criteria`, one entry per criterion that is on with its id, name, colour, mode, carving numbers, voxels at start and kept volume, and `chain`, the volume each criterion kept and the share of the maximum volume the last one kept. A criterion without results is listed with empty numbers, and `chain` is null until every criterion has results.
- `.../run/score-points` and `.../run/sky-patches` take an optional `criterion` and default to the last criterion that is on.
- `.../run/skipped-surfaces` gives the test surfaces a criterion's run left out, with the reason and their triangles, and `null` when it left none out.
- `.../run/sky-patches` answers `null` for a run that has no sky patches (time-based and tilted plane runs), and `.../studies/{id}/sky-patches` does for a sun hours study: these are answers, not failures. A 404 means the criterion or the study has not run. When a run's sky patches cannot be read (a damaged file), **Layers** lists the sky dome as missing and says how to write it again. A file that preprocessing wrote and that is gone from the project folder makes the stage missing, so **Run analysis** comes back and writes it again.
- `.../run/carved-by-criterion` serves which criterion removed each voxel: a 4-byte little-endian header length, a JSON header (`origin`, `shape`, `voxel_size`, `criterion_ids`, padded with spaces to a multiple of 4 bytes), then one byte per voxel of the grid in C order, 0 for a voxel the last criterion kept or one that is empty, and *k* for a voxel removed by the *k*-th criterion that is on. It answers 404 until every criterion that is on has thresholding results on the same grid.
- The run report has a Criteria section with one row per criterion (see [Criteria](criteria.md#output-folders)).

## Entering values

A number with a range is entered with a slider and a number field side by side. The number field takes any value the engine accepts; the slider covers the range people normally use (for example 0.1 to 5 m for the voxel size). The balance temperature and the analysis period are strips with two handles instead, each handle with its exact value in a bubble over it, always shown; where the two handles are close, their bubbles move apart so they never overlap.

- **Balance temperature** (Solar heating) is a strip from 10 to 30 °C, with a tick a degree and a label every 5 °C, and two handles, the two ends of the dead band, with the band between them filled. The lower end (named "Counts below" for a screen reader) is where sun starts to count: in hours colder than this. The upper end ("Too warm above") is where, with harm counted, hours warmer than this count against the sun. Each end moves on its own and cannot pass the other; the app sends the engine the middle as `balance_temperature` and half the width as `balance_offset`, the dead band the engine reads on both sides of the balance temperature. A press on the strip moves the nearer handle there, to the step of 0.5 °C; the arrow keys move a handle by 0.5 °C, Page Up and Page Down by 2 °C, Home and End to the ends of the strip. A value outside 10 to 30 °C (from a hand-edited `config.yaml`) pins its handle at the end of the strip, and its bubble shows the value. The lower handle comes first for Tab, as on the strip; where the two handles lie on one spot, the direction picks the end: a drag to the left or an arrow key toward the lower end moves the lower one, and to the right the upper one, the focus moving to that end's handle. Home or End on one spot take the lower or the upper end to the end of the strip.
  Without harm counted (**Subtract summer overheating** off) the upper end does nothing, so the strip has one handle, and the setting is named **Sun counts below**, with help that says so; the fill runs from the start of the strip to the handle. That handle moves the whole band, keeping its width, so turning harm on brings back the upper end at the same distance. Simulate's study settings draw the strip the same way.
- **Sample spacing** on the test surfaces is not set in the browser: the engine samples them at half the voxel size, and a quiet line under Voxel size says so ("Test surfaces sampled every 0.5 m"). On the District example (Solar heating, 1 m voxels) half the voxel size differs from a 0.25 m reference in 0.9 % of the kept voxels, against 2.0 % for a spacing of 1 m, at about twice the analysis time (13.9 s against 7.1 s; 0.25 m takes 37 s). A project that stored a sample spacing (an earlier version let you set one) drops it when it opens, so its analysis shows as out of date once if that spacing was not half its voxel size. An analysis made before this change without a stored spacing sampled every 1 m, the old default, so it too shows as out of date once unless its voxel size is 2 m. In `config.yaml`, on the command line and in Grasshopper `grid_step` can still be set.
- **Units.** Every number shows its unit beside the value: counts say what they count (Smoothing passes in passes, Rays per batch in rays, Cut voxels in voxels, "1 voxel" for a count of one), and Sun positions per hour reads "12 per hour (every 5 minutes)".
- **Drop pieces smaller than** is shown and typed in m³, though the engine stores `min_voxels`, a count of voxels: the form multiplies the count by the volume of a voxel at the voxel size it shows (300 voxels at 0.5 m read 37.5 m³) and turns a volume typed back into whole voxels, at least one. The stored count does not change when the voxel size does, so the volume shown follows the voxel size.
- **Grid margin** (`margin_frac`) is hidden for now; the engine's default (1 % of the longest side) applies, or a value already in `config.yaml`.
- **Ray length** (`ray_length`) has no field: rays stop where they leave the voxel grid, so the engine's default of 3000 m reaches across any grid at no cost. A value already in a project's `config.yaml` is kept and applies.
- **Edge strip with less weight** (`edge_taper`) is shown in Night cooling only, under **More mode settings**: sample points closer than this to the edge of a test surface count less, from 0 at the edge to full at this distance, so a cooling street or courtyard does not clear the mass right beside it. 0 is off. The engine reads it in every weighted mode: a value already in a project's `config.yaml` is kept when the project opens, in any mode, and dropped when you choose a mode that does not show it. A value set there stays in the other weighted modes, which read it: their settings say so in a line.
- **Analysis period** is one control with two strips.
    - The year strip has twelve months and two handles for the start and the end date, each with its date in a bubble ("21 Dec"). A period across the new year (start after end, as in October to April) is drawn wrapped.
    - A click on a bubble, or Enter on its handle, turns the bubble into a text field with its value selected. A date is typed day first, as the bubbles show it ("21 Dec", "21 december", "21/12", "21.12"), or month first ("Dec 21"); an hour as "10", "10 h" or "10:00". Enter sets it; a text that names no date or hour (30 Feb, 25 h) marks the field and keeps it for a correction; Escape or leaving the field puts the bubble back unchanged.
    - The hour strip has two handles for the first and the last hour, each with its hour in a bubble ("10 h"). A line under the strips counts the days and the hours a day. The last hour is inclusive, so 10 to 14 h samples 10:00 through 14:00. A range across midnight is drawn wrapped.
    - A drag is sent once, when you let go; a key or a preset is sent at once. A period not set yet says "Not set yet" under the strips.
    - Presets set the dates and keep the hours: 21 December, 21 June, Heating season and Whole year. The heating season follows the hemisphere of the weather file's latitude: 1 April to 31 October south of the Tropic of Capricorn (23.44 degrees), 1 October to 30 April elsewhere, within the tropics and without a weather file.
    - In Solar heating with Cold hours a fifth preset, **Cold period from the weather file**, named by its dates once found, sets the dates of the site's cold period: the longest run of days whose mean temperature over the month around them is below the balance temperature minus the dead band. Its tooltip, shown while the pointer is over the button or the keyboard focus is on it (Escape closes it), says what it found ("Cold period of the weather file, where the mean of the month around each day is below 13 °C: 30 Sep to 15 May."), or why it cannot be used yet: no weather file, no cold period in it, or a failure to read it. A screen reader reads the same text as the button's description. It needs the weather file. Changing the balance temperature later updates that text but not the dates already set; press the preset again to use the new ones. Solar heating already counts only the hours colder than that threshold, so the cold period mostly leaves out cold hours outside the heating season, such as cool summer mornings; it changes more when the experimental "include harm" option is on, whose warm hours depend on the period.
    - When you add or replace the weather file (not when a project opens with one), the Criteria step shows one notice about the new file, with two buttons; either button closes it, and a later weather file replaces it. In Solar heating with Cold hours it offers the cold period of the new file when its dates differ from the period's (with Energy-weighted it offers nothing: the cold period belongs to the cold hours rule), keeping the hours ("The new weather file (Brisbane, AUS) has its cold period from 3 May to 20 Sep; the analysis period is 30 Sep to 15 May.", **Use the cold period** or **Keep**); it waits for the cold period and shows nothing when the file has none. In Sun hours and Solar energy it appears only when the new file is in the other hemisphere from the one before (a project without one counts as northern, as the starting values are), and offers the same dates six months on: the month plus six, the day held to the month's length, the last day of a month staying the last day (30 Apr gives 31 Oct). For example "The new weather file (Brisbane, AUS) is in the southern hemisphere: winter there is June to August. Shift the analysis period by six months, to 21 Jun, 10 to 14 h?", **Shift by six months** or **Keep**. A period that covers the whole year covers the same days six months on, so it gets no offer. A file within the tropics, or one whose latitude cannot be read, brings no offer, and the hemisphere of the file before it still counts for the next one. The offer is saved as any change of the period is; while a run is in progress the buttons are disabled, as the settings are. Either button moves the focus to the analysis period's start date. Once the period changes, by the button or by hand, the notice is gone and stays gone if the period is set back; choosing a mode without an analysis period (Angle rule, Daylight, Night cooling) dismisses it too. Screen readers announce the notice as it appears.
    - Each handle takes the keyboard: the arrow keys move it by one day or one hour, Page Up and Page Down by a month or six hours, Home and End to the first or last day or hour.
    - When the hours cross midnight on a single date, the end date moves to the next day ("21 to 22 Dec, 22 to 2 h"). A period stored earlier with one date and hours across midnight (an older save or a hand-edited `config.yaml`) is what the engine runs on every day of the year: the year strip is filled whole and a note under the strips says so: "Every day, 22 to 2 h: the hours cross midnight on one date, which the engine runs on every day of the year. The next change makes it one night." The period is not written until you change it.

## Running: two phases

A run has two phases, so that the part that takes time happens once and the part you adjust is quick.

1. **Run analysis** runs the sun analysis and the carving (the preprocessing and thresholding stages). The 3D view then shows the kept voxels coloured by score; the carved voxels are a separate layer, hidden at first, which the Layers menu shows. The progress shows the stages, the ray batches and the elapsed time, with a Cancel button. With several criteria it does this for the criteria that changed (see [Runs](#runs)).
2. **Build envelope** and **Build massing** (in Envelope and massing) run on the voxel result you settled on in the Criteria step: the exporting stage and the massing stage. **Build envelope and massing**, pinned in Criteria, builds both.

Between the two you change the threshold. The cutoff line on the histogram can be dragged in every rule, or moved with the keys of its handle (arrow keys a hundredth of the range, Page Up and Page Down a tenth, Home and End to the ends). While it moves, a line under the histogram previews the share of the volume the cut keeps, worked out in the browser from the voxel scores of the last carving, before the slope limit (the run gives the exact numbers); in the weighted modes it also gives the carve amount the cut stands for, which the slider shows. Letting go sets that carve amount (under Automatic it switches the rule to Manual, and the step says so), or in Sun hours the cutoff itself, whose slider ends at the highest score the cutoff is compared with (after *Remove everything above a cut*), past which a cutoff carves nothing more. Choosing Manual starts from the amount the cut on the histogram carves. With several criteria the line, the slider and the update belong to the selected criterion (see [Several criteria](#several-criteria)). Moving the slider or typing a value moves the line too. With **Update the carving as I change its settings** on in [Project settings](#project-settings) (the default), each change is applied as you let go of the line or the slider or leave the field: the scores are thresholded again without repeating the analysis. Off, **Update carving** applies it, in the bar pinned under the steps or on the view's **Out of date** stamp; until then the line stays where it was set, drawn in the accent colour as a preview. The choice is kept in the project (`project.json`), for every criterion; one an earlier version kept in the browser is moved into the project when the project opens.

The interface keeps track of what each result was built from. When you change a setting or an input after a result exists, that result stays visible, dimmed and labelled out of date, and the step that needs a run says so. While a dimmed result is shown in the 3D view, an **Out of date** stamp sits at the top of the view (**Updating** while a run replaces it), and goes once the results are current. In Carve it holds the run the pinned bar offers, **Update carving** or **Run analysis**, disabled with the reason when a run cannot start; it never runs Simulate's studies, and in Simulate and Inspect it has no button. Running again replaces it. A run only starts the stages whose results are missing or out of date.

While the mode or the analysis settings in the form differ from the stored ones, the carving is locked, because a build would have to run the analysis first. The two builds then wait with a message to run the analysis again, and a mesh format change is stored and written by the next build of each part.

## The 3D view

The view has a compass, an axis gizmo (the three lettered axes, drawn straight on the viewport) and a legend for the coloured layers. The **Layers** menu switches the maximum volume, the test surfaces, the context (neutral grey massing) and the terrain (a ground surface), both shown in every step, the kept and carved voxels (with several criteria also the carved voxels by criterion), the sun path, the sky dome, the carved envelope and the building massing. Buttons frame the whole model, show the top view and switch the ground aid (the ground grid, the compass ring, or neither). The sky dome shows after a run where the step shows it, so a first run of a sky-based mode shows what it weighed; hidden in the Layers menu, it stays hidden on this computer (kept in the browser) until shown again. The viewport is light or dark with the app's theme (the theme button in the top bar).

The ground aid button cycles through three states: off, a ground grid with a scale bar, and a compass ring on the ground around the scene (ticks every 10 degrees, the letters N, E, S and W every 90 degrees, rotated by the north direction). The button names the aid it switches to, and the choice is remembered in the browser. The compass ring, the sun path and the sky dome are centred on everything loaded (the maximum volume and the test surfaces together). Their hemisphere has a radius of 0.75 times the larger horizontal side of those together, and at least their height, so it encloses them without dwarfing them. Framing the model leaves out the surroundings and the terrain, which can reach far beyond the site. The camera orbits about the centre of the compass ring, at the middle height of the maximum volume, so the ring stays in place as you turn; when the ring moves (a test surface file loaded or added further out), the orbit point moves with it. Frame all, the top view and the first framing fit the visible layers around that point, in the part of the 3D view that no panel lies over: the Studies panel in Simulate, the Geometries panel in Inspect, and the step panel when a window under 1100 px wide lays it over the view. The orbit point stays in the middle of that part as the window is resized or a panel opens, closes or changes size. Panning (the right button, or Ctrl or Shift with the left) moves the picture on the screen and leaves the orbit point where it is, so turning the view after a pan still turns it about the compass ring's centre; framing brings the picture back. A tooltip that would cover the pinned **Run analysis** bar when it opens under its "i" opens over the "i" instead.

## Simulate

The switch **Carve | Simulate | Inspect** in the header, next to the project name, opens a workspace beside the pipeline that checks how much sun, solar energy or sky reaches the test surfaces, the context, the ground or the new building itself, with the maximum volume, the carved envelope or the massing standing. [Simulate](simulate.md) explains the metrics and what they block. Simulate changes no criterion, setting or pipeline step, and runs nothing until you press **Run**.

- Simulate hides the four steps and gives the 3D view the whole window. Switching back to Carve returns to the step you left, with its folds and scroll position kept.
- The **Studies** panel floats over the top left of the view and collapses to an icon. Each row is a study: a colour swatch, its name (whole, on up to two lines; the whole on hover) and a line (its study surfaces, **Out of date**, **Not run yet** or why it cannot run). Pressing a row puts that study on the view; only one is shown at a time. Its settings button opens a popover with the name, the metric, the analysis period, **More settings** (with the test point **Spacing**, which follows Carve's until you type one), the **Study surfaces**, **Duplicate study** and **Delete study**. Changes are saved at once.
- A study's **Study surfaces** (Simulate's name, apart from the criteria's test surfaces): **Account for** (a list) chooses what stands on the plot (**Nothing**, **Max volume**, **Base volume** while the project has a base height, **Envelope** or **Massing**; the last two wait until Carve has built them). **Base volume** is the part of the maximum volume below the base heights: what stands now, or may be built anyway, to compare with the envelope. When the base height of a study on the base volume is set back to none or 0, the study waits: its row says "Set a base height in Settings", **Run** leaves it out, and its choice reads "Base volume (set a base height in Settings)". The studies are read again whenever the sites, their heights or the source of the maximum volume change, also from Settings while Simulate is open. Under **Simulate**, switches choose what is measured: that geometry's own facades and roofs, **Context** (greyed until the project has context files), and **Terrain** when the project has a terrain file, else **Ground** (a flat disc on the compass circle), then each of the project's test surface files. A study needs at least one surface to simulate; the row's line names them, for example "the massing, facades.obj, the context".
- **Add study** lists the criteria as **Like *name*** (the metric of its mode, its period, mode settings and files, copied) and the metrics (a metric that needs a weather file is greyed without one). **Run** runs every study that can run, each with the geometry it accounts for and with nothing built.
- One job runs at a time. While a carving run is going Run says "A carving run is in progress", and while a simulation is going Carve's run buttons say so.
- The legend along the bottom colours the values by the study's unit (the default) or by **% of no-build** (each point's share of its value with nothing built on the plot, the surroundings and terrain still blocking; 0 to 100 % for every geometry). Two marks set the low and high end of the colours (drag them, or use the arrow keys; Delete puts one back): the palette runs between them and values beyond an end take its colour. An end stays 1 % of the bar short of the other. By value the low end is the study's **target**, and both ends are saved with the study; new settings or a new metric clear them, so the next run shows its own range. The palettes are fixed: Magma by value, Viridis by share. The result card in the bottom right corner gives what the points keep of the no-build value, the mean, the lowest tenth and the share of points at or above the target ("92 % at or above the target"); a study that simulates its geometry's faces has a second block for the building, with a table by facing (roofs, north, east, south, west) in a fold. The card minimises to its title. When no study is selected the first one with a result is.
- The **Sun** button in the view's toolbar, in every workspace, opens the sun tool under the toolbar (it needs the weather file): the year's sun path with a day while it is open, and, on a switch, the shadows at a moment (a day and a time, each on a strip with one handle). Its clock, at the end, reads the times in local standard, solar or daylight saving time. The hours of sun over a period are a Sun hours study, with a **Quick count** switch. The **Show** switch beside the studies panel's title hides the selected study from the view.
- The **Sky dome** layer shows the selected study's sky patches, each coloured by the value it carried in the study's last run (none for sun hours); Carve's dome is not shown in Simulate.
- A result whose inputs changed stays on the view with the **Out of date** stamp, drawn in grey, still opaque (other out-of-date layers fade to a grey). Reopening the project shows the last results.

## Inspect

The switch **Carve | Simulate | Inspect** in the header also opens Inspect, a workspace beside the pipeline that shows which way the test surfaces face and summarises the input mesh files. [Inspect](inspect.md) explains it in full. It runs no engine step, and only **Save** and **Restore original** change a file.

- Inspect hides the four steps and gives the 3D view the whole window. Switching back returns to the step you left.
- The **Geometries** panel floats over the top left of the view and collapses to an icon. It lists the maximum volume, test surface, surroundings and terrain files, each with its triangle count and area; pressing a row frames the file in the part of the view the panel does not cover, draws the other test surface files faint and opens its bounds and (for test surfaces) surface count. A file the app cannot read is listed with its problem.
- Test surfaces are drawn two-sided: the side the normal points to in the test surface colour, the back side in orange, so a surface the wrong way round shows orange from outside. **Face normals** draws one normal per surface.
- On a test surface file, **Flip mode** turns the whole surface under a click (a second click turns it back) and **Flip all** turns every surface. Turns are staged and shown at once; **Save** writes the file once in its own format, **Discard** drops the turns, and **Restore original** puts back the file as it was before the first save. A file that is closed as a whole cannot be flipped.
- Save and Restore original act like an upload: the criteria and studies that list the file go out of date. They wait while a run of the project is going. If the file was replaced in the project folder since Inspect read it, they write nothing and say so, and its staged turns are dropped.
- Leaving Inspect with turns not saved, or while a save is under way, asks Save, Discard or Stay. A save under way is said in the dialog, and if it is refused the dialog stays open with the reason.

## Where projects are kept

Each project is a folder in the projects folder:

```
<projects folder>/<project name>/
├── inputs/        The files you added (max_volume/, test_surfaces/, context/, terrain/, weather.epw)
│                  and the joined meshes the engine reads (joined/, one test_surfaces_<id>.ply per criterion
│                  and one study_surfaces_<id>.ply per study that lists files), and originals/test_surfaces/,
│                  the test surface files as they were before Inspect first saved a flip of them
├── config.yaml    The settings, a normal USC chain file (shared settings, then the criteria that are on)
├── project.json   The project's record: the files you added with their triangle counts, size, time and digest,
│                  the notices of files replaced in the folder, the input revision,
│                  the example it came from (if any), the criteria with their own settings and test surface files,
│                  the studies of Simulate, the sites and whether the maximum volume is made from them (max_volume_source),
│                  and one record per completed stage (with the settings that stage ran with)
├── run/           The engine's output: criteria/<id>/preprocessing and thresholding, criteria/chain.json,
│                  exporting/ and massing/
└── simulate/      The results of the studies, one folder per study (see Simulate)
```

`config.yaml` works outside the interface: its paths are relative to the project folder, so `usc run -c <project folder>/config.yaml` runs the same analysis from the command line (see [Criteria in a project](#criteria-in-a-project)). Thresholding also writes `scores_compared_with_cutoff.npy` in its folder (the values the cutoff is applied to, which the histogram draws). To delete a project, use Delete in its menu (see [Managing a project](#managing-a-project)), or delete its folder in the file manager.

### Replacing a file in the project folder

You can save a new version of an input file over the old one in `inputs/` (an export from Rhino saved over `inputs/test_surfaces/roofs.obj`, say), keeping its name. The app finds the change when the project is opened, when it asks for the stage status (after a save, a change of the inputs or a run, and whenever its window comes back to the front), when it lists the studies, and when a run or a simulation starts. A file that was added in the app is read again only when its size or modification time differs from what `project.json` recorded (`stored_files`); the same content saved again changes nothing.

A file whose content changed is built into the joined files that use it, in place of the old version:

- A test surface file: the joined files of the criteria and studies that list it. Those criteria are out of date, and the criteria after them have to carve again; the studies that list it are out of date.
- The maximum volume, the context or the terrain: the role's joined file. Every stage and every study is out of date.
- The weather file: every stage is out of date, and so are the studies whose metric reads it.

A notice over the steps (and at the top of the Studies panel in Simulate) names each changed file, until you press **OK**. The 3D view loads its meshes again. A joined file that comes out the same (a file saved again with the same surfaces) changes nothing and gives no notice; for the context and the terrain, whose orientation nothing reads, a face turned the other way is the same face. While a run of the project is going, the app waits for it to end before it looks.

A file of a project made before this check has no record. The first look builds its joined files and compares them with those the runs used, so a file replaced earlier is caught too. A weather file without a record is taken as it is.

A file the app cannot read (a broken export, or one still being copied or locked by another program) is not built in and is tried again at the next look; the project still opens, and a run says which file it is. A file deleted from the folder is listed as missing. A run is refused while a file it reads is missing (a test surface file of a criterion that is on, or a file of another role), and a simulation while a file the studies read is missing, until you put it back or remove it in the app. A file added to the folder by hand, under a new name, is not seen: add it in the app.

## Security

The service listens on `127.0.0.1` only and checks the `Host` header of every request, which stops a web page on another site from reaching it. Every request to the API needs the token of the launch, which only the printed and opened address carries, and the service takes no file path from the browser: it derives every folder from a validated project name, and the folder picker is shown by the service on this computer.

## Without a CUDA-enabled GPU

When no CUDA-enabled GPU is found, the top bar says "CPU mode" (the reason on hover), the start screen's footer gives the reason, and the engine runs on the CPU. The results are the same, and an analysis takes noticeably longer, so start with a larger voxel size or with the smallest example. `--device cpu` chooses the CPU even when a GPU is present.

## Rebuilding the front-end after changing `app/`

The interface is a React and three.js application whose source is in `app/`. The package carries its built files in `src/urbansolarcarver/ui_static/`, so using `usc ui` needs no Node.js. After changing `app/`:

```bash
cd app
npm install
npm run typecheck  # tsc --noEmit: the type check alone
npm run build      # runs the type check first, then writes src/urbansolarcarver/ui_static/ and build_info.json
npm test           # the front-end tests
```

A type error stops `npm run build` before anything is written.

Commit the rebuilt `ui_static/` with the source change: a test compares the hash in `build_info.json` with the sources and fails when they differ.

If the service's API changed, regenerate the client types with `npm run api-types`. It finds the repository's `.venv` itself, also from a git worktree without an environment of its own, and reads that checkout's sources.
